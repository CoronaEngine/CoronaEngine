CoronaEngine · Storage → EnTT 架构设计

删掉 13 个 Storage：用 ECS 重建 DAG 的内部存储与外部边界

目标是把 SharedDataHub 的所有 Storage 容器清空，DAG 内部改成 EnTT registry；外部线程不再碰任何槽位——写只走命令，读只拿快照。这不是一次容器替换：它同时改掉了句柄语义、生命周期、网络身份和整个公开 API。

五条不可协商的原则

  1. 单写者。registry 只允许 DAG 线程访问；没有锁，也不打算加锁。任何外部线程拿到 registry 引用都是设计错误，用线程断言和头文件边界把它挡在编译期/运行期之外。
  2. 身份稳定。外部拿到的句柄是 index + generation，不是组件地址。ECS 的 archetype 搬移会让组件地址随时失效，裸指针绝不能离开 DAG 线程。
  3. 写命令、读快照。没有第三条路。命令是唯一写入口，快照是唯一读出口；两者都只传值、不传指针。
  4. 结构变更延后。创建/销毁/挂载组件统一在 tick 边界执行，tick 中间不做 archetype 搬移，保证系统遍历期间视图稳定。
  5. 组件按变更频率拆，不按旧结构体一比一映射。每帧变的（Transform/Skinning）和加载期变的（MeshSet/ModelSource）分开，避免整块组件被高频系统反复拉进 cache。

这个方案真正换掉了什么

句柄语义

从“槽位内存地址”变成“实体 id + 代际”。旧句柄在实体销毁后会被 generation 拒绝，而不是像现在一样指针悬空。

访问路径

Geometry 现在每个 actor 要链式拿 5 把锁（scene→actor→profile→mechanics→geometry→transform）；ECS 下一次 view 遍历直接拿到全部组件。

网络身份

现在同步依赖 seq_id（槽位物理序号），要求两端布局一致，创建 actor 时甚至要暂停同步；ECS 没有等价物，必须切到 GUID + revision。

03快照、命令与身份

快照契约

每 tick 一次不可变投影非全量revision 单调
  • 发布点只有一个：tick 末尾，所有系统跑完之后。快照 = 该 tick 的最终状态。
  • 内容只有投影：actors（位姿/可见/驻留）、cameras（位姿/输出/视口/timing）、scene、stats，合计约 38 个字段；蒙皮、网格、IK、材质内部一律不进。
  • 所有权：发布者填好一个只读对象后原子换指针；读者拿到 shared_ptr<const WorldSnapshot>，生命周期与 DAG 解耦。
  • 一致性：单对象内所有字段来自同一 tick；不同对象之间可能差 1 个 revision（120Hz 下 8.3ms）。
  • 结构变化：实体的创建/销毁通过事件通知；快照里不会出现“半初始化实体”。

命令契约

双缓冲按实体合并tick 边界应用可回执
  • 连续量（拖拽、相机移动、滑动条）：按实体合并，只保留最后一条，带 sequence。
  • 离散量（创建、销毁、挂载、显隐）：FIFO，不合并，失败要有 error 回执。
  • 结构命令单独一个阶段：先应用 create/destroy/attach，再应用属性命令，最后跑系统。
  • 背压：队列有界；连续量丢最旧，离散量拒绝并回事件。

身份：三套 id，各司其职

标识形式生命周期用途
entt::entityindex(20b)+version(12b)，32 bitDAG 内部registry 内部索引；不出 DAG 线程。
EntityHandleindex(24b)+generation(16b) = 40 bit实体存活期外部命令与快照的快速身份；< 2^53，可安全穿过 CEF 的 double。
ActorGuiduint64 / 字符串永久持久化、网络同步、场景引用；跨进程唯一，替代 seq_id。

规则：句柄可以随实体销毁而失效（generation 拒绝）；GUID 永不失效。命令里能用句柄就用句柄，跨越进程/存档一律用 GUID。

什么不进 ECS

FrameExchange

GPU 帧的句柄 + 提交收据 + 消费回执。它是“跨线程传递 GPU 资源”的协议，不是游戏状态。

Telemetry

tick 耗时、相机 render/denoise 耗时。ring buffer + 只读视图，写者单一、读者无锁。

ViewportChannel

视口 UI 模式、gizmo hover/drag。编辑器会话状态，走命令 + 事件，不进世界。

判定标准：它是不是“世界状态”？能被存档、能被网络复制、能被系统按实体遍历的，进 ECS；描述“怎么把世界画出来/怎么交互”的，留在边界结构里。

04迁移路线：五个可独立交付的阶段

原则：每个阶段都能单独合并、单独回滚；不允许“大爆炸式”一次性替换。点左侧阶段查看任务与验收门槛。

阶段之间的硬依赖

P1（外部读改成快照）必须先于 P3（重系统组件化）——否则组件化时外部还在直读槽位，会同时改两边。
P2（身份与结构变更）必须先于 P4（删容器）——否则网络与句柄还在依赖 seq_id/地址。
P0 的 snapshot 投影可以先只覆盖相机与 transform，随后每阶段扩字段。

07口径

      

        
数字来源
Storage 数量与字段数来自 include/corona/shared_data_hub.h；锁调用与访问器调用点来自 src/ 静态统计；154 个外部字段来自本仓库的边界审计文档。工作量级 S/M/L 是相对估算，不是承诺。

        
这个设计没有覆盖什么
  • 渲染管线内部（Optics 的 pass 组织、Vision 的 RT 管理）不因 ECS 改变。
  • 资源系统（ResourceManager）仍按资源 id 管理，ECS 只挂句柄/组件。
  • 编辑器前端（CEF JS / Python）的 API 迁移只给了策略，没有逐个函数改写。
