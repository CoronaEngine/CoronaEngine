# Kitchen CPU 场景同步优化方案

- 日期：2026-09-27
- 状态：第 3 节路径优化已完成实现、回归、正式构建和性能实测；第 2 节 AABB 优化尚未实施，整体优化方案未全部完成。
- 目标：减少静止场景的重复 CPU 工作，同时保持包围盒、可见性、几何同步和渲染行为正确。

## 1. 已有测量依据

测试环境为 RTX 3070 Ti、CLion RelWithDebInfo 构建；kitchen 有 299 个物体，单静止相机，实际 framebuffer 为 1536×825。渲染为 1 spp、最大深度 16；当前 PT 模式实际启用 SVGF。

正常路径的新场景帧间隔平均为 187.51 ms，约 5.33 FPS；UI 主循环间隔为 18.61 ms。UI、显示与场景渲染分别运行，不能将各线程时间直接相加。

对 `OpticsSystem::sync_external_live_vision_transforms()` 进一步计时：预热 20 秒后采样 25 秒，共 136 帧，全部样本 `changed=false`。

| 同步内部操作 | 平均耗时 | 同步内占比 |
|---|---:|---:|
| 逐三角形重算 AABB | 131.152 ms | 79.52% |
| 规范化源文件路径 | 31.581 ms | 19.15% |
| 扫描原始实例缓存 | 0.489 ms | 0.30% |
| 读取变换及计算签名 | 0.326 ms | 0.20% |
| 其他绑定、集合与记录维护 | 1.389 ms | 0.84% |
| 合计 | 164.937 ms | 100% |

每帧调用 `init_aabb()` 299 次，遍历 1,443,303 个三角形，执行约 4,329,909 次顶点坐标变换；路径规范化同样调用 299 次。前两项合计占同步时间的 98.66%。

细分采样与整帧基线来自不同轮次，存在运行波动；不能混合不同轮次的均值计算精确加速比。

本机原始证据位于 `cmake-build-relwithdebinfo/kitchen-frame-profile/`：

- `baseline2.summary.json`、`baseline2.frames.csv`：正常路径整帧基线。
- `sync-detail.summary.json`、`sync-detail.frames.csv`：同步内部细分。
- `sync-detail.stdout.log`、`sync-detail.window.json`：原始日志及采样窗口。
- `sync-detail-instrumentation.patch`：临时计时补丁，采样后已撤回。

上述构建目录可能被清理，因此关键基线数值同时保存在本文。

## 2. 第一项改动：未变化物体复用包围盒

### 当前问题

同步函数已经计算 `actor_signature_changed`，但随后仍恢复实例记录、设置实例矩阵、逐三角形重算 AABB。函数末尾的 `if (!changed) return` 仅跳过后续 GPU 更新，重复 CPU 工作已经完成。

主要位置：

- `src/systems/optics/optics_system.cpp`：`sync_external_live_vision_transforms()`。
- `vision/src/base/shape.cpp`：`ShapeInstance::compute_aabb()`。
- `include/corona/systems/optics/vision_scene_resource.h`：同步签名、形状记录与逻辑实例缓存。

### 方案

复用现有变换签名和形状记录，在清空 `group->aabb`、恢复实例、写入矩阵、调用 `init_aabb()` 之前判断能否跳过更新。

快速路径必须同时满足：

1. 该物体已经完成首次同步，相关实例与包围盒缓存有效。
2. 形状身份、实例集合和几何内容未改变。
3. 物体变换及可见性未改变。
4. 场景资源或该运行时的状态未因重建而失效。

满足条件时复用原矩阵、实例记录和 AABB。不能先清空组包围盒再跳过，也不能因跳过变换更新而遗漏形状增删或元数据维护。

### 必须保留的更新情况

| 变化 | 必须执行的处理 |
|---|---|
| 首次加载或首次绑定 | 完成原始实例缓存及首次同步 |
| 移动、旋转、缩放 | 更新实例矩阵、包围盒及相关 GPU 变换 |
| 隐藏、恢复显示 | 应用隐藏状态或恢复正确实例状态 |
| 网格替换、顶点变形 | 即使物体变换未变，也更新相关包围盒 |
| 实例增删、形状身份变化 | 更新形状记录、实例集合及相关缓存 |
| 场景重载、资源重建 | 使旧缓存失效并重新初始化 |
| 多视图或多个渲染运行时 | 保留各运行时消费共享场景变更的版本与上传机制 |
| 仅移动相机 | 不触发物体世界空间 AABB 重算 |

实施前必须核实几何变化和缓存失效的现有信号。不能只比较物体变换签名；若某类变形或重建缺少可靠判定，应保留该路径的完整更新，直到其失效规则明确。

保持现有逐三角形 AABB 算法，首次实施只减少调用次数。光照、ReSTIR 等消费者继续读取正确的场景范围。

## 3. 第二项改动：加载或绑定时生成规范化路径键

当前每个物体都调用 `normalize_scene_path_key(binding->source_path)`，内部包含 `std::filesystem::weakly_canonical()`、字符串转换及规范化。

采用加载阶段预处理：在场景加载、绑定创建或源路径变化时生成规范化键，稳态同步直接比较键。

```text
source_path：保留原始来源信息，用于持久化及项目迁移
source_path_key：根据明确的场景/项目基目录生成的运行时规范化键
```

已核实：绑定创建和修改通过 `SharedDataHub::set_external_vision_binding()` 写入私有绑定表。Actor API、编辑器可见性修改及形状索引回写均经过此入口，可在此统一维护键的有效性。

实施规则：

1. 加载入口明确相对路径所依赖的场景/项目基目录，不能依赖之后变化的进程工作目录。
2. 场景资源键与绑定键使用同一套规范化规则及错误处理；将现有规则提取到合适的共享位置，避免两套实现产生不同结果。
3. `ExternalVisionBindingDevice` 增加运行时派生键；统一写入入口在首次绑定或源路径/基目录变化时计算并发布完整绑定。原始路径保持独立，派生绝对键不作为可移植项目的持久化身份。
4. 只有可见性、形状索引等无关字段变化时复用有效键，不再次查询文件系统。文件系统解析在共享元数据锁之外完成。
5. 逐物体同步及其他绑定来源检查直接使用已生成的键；缺失键在加载/绑定入口补齐，不能退回每帧逐物体解析。
6. 更换源文件、修改路径或基目录、项目迁移、场景重载及绑定重建时重新生成键。物体或相机移动不使路径键失效。
7. 若支持运行中修改目录链接并立即生效，该操作必须显式触发重新绑定或刷新；普通帧循环不轮询文件系统变化。

验收目标为稳态每帧绑定源路径规范化 **0 次**。同一场景大量绑定的首次加载还可复用该场景已经生成的规范化键，但统一入口必须保证键与源路径及基目录一致。

本方案替代此前的帧内缓存方案；运行时不再为同一条绑定源路径每帧重新规范化一次。

## 4. 改动范围与顺序

以下为两项优化的整体计划。2026-09-27 本轮经用户批准只实施第 3 节路径优化；AABB 的快速路径及其专项验收留待后续。

1. 核实首次同步、几何变更、隐藏恢复、运行时重建的状态流与现有测试。
2. 补充与实际变更对应的行为回归验证。
3. 在同步函数中加入未变化物体的快速路径；优先复用已有状态，必要的失效记录放在现有场景资源中。
4. 在加载/绑定入口统一生成和维护路径键，将同步侧及其他绑定来源检查改为键比较。
5. 使用项目规定的 CLion 构建脚本编译，完成正确性验证。
6. 用同一场景、相机、分辨率及渲染设置复测，记录优化后数据。

预计生产代码涉及 `src/systems/optics/optics_system.cpp`、`include/corona/shared_data_hub.h`、`src/shared_data_hub.cpp`，以及必要的共享路径规范化工具和加载入口。AABB 只有确认现有状态不足时才调整场景资源记录。测试优先复用现有 optics 和绑定元数据测试设施。

构建命令：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .agents/skills/clion-build-corona-engine/scripts/build.ps1
```

本轮不更换 AABB 算法，不调整 PT、SVGF、分辨率、采样数或最大深度。原始实例缓存索引优化只有约 0.49 ms 的当前成本，留待两项主要改动验证后再决定。

## 5. 验收标准

| 验证项 | 通过条件 |
|---|---|
| 静止 kitchen | 预热后未变化物体的 `init_aabb()` 调用为 0 次/帧 |
| 稳态路径比较 | 绑定源路径规范化 0 次/帧；直接读取派生键 |
| 路径初始化和刷新 | 新绑定、改路径、改基目录、迁移/重载时生成正确键 |
| 路径等价和场景隔离 | 等价路径映射到相同键，不同源场景不串绑；覆盖相对路径、分隔符、大小写和 `..` |
| 无关绑定修改 | 仅修改可见性或形状索引时不重复解析路径 |
| 移动、旋转、非均匀缩放 | 更新后的包围盒与原算法结果一致，允许约定浮点容差 |
| 隐藏与恢复 | 实例及包围盒状态正确恢复，无漏更新 |
| 网格替换及顶点变化 | 物体变换未变时仍能正确更新 |
| 增删、首次加载、重载 | 无无效实例记录、旧包围盒或初始化遗漏 |
| 多视图与渲染模式切换 | 各运行时均获得实际变更，不显示过期几何状态 |
| 相机移动 | 渲染视角正常更新，不导致静止物体 AABB 重算 |
| 构建与回归 | 规定构建成功，相关行为测试通过 |
| 性能复测 | 保存同步与新场景帧的均值、P95、样本数和测试条件 |

不能仅凭计数减少判断正确性；还需检查矩阵、包围盒和渲染行为。随机渲染噪声不应被误判为功能回归。

## 6. 性能目标与完成条件

静态场景 CPU 同步目标为从约 165 ms 降至数毫秒量级。该目标基于现有热点成本，不是优化后已测得的结果，也不承诺固定 FPS。

复测沿用至少 20 秒预热、25 秒采样，并确认实际 framebuffer、相机姿态、SVGF 状态等保持一致。分别记录：

- 同步函数总耗时、AABB 重算次数与耗时、路径解析次数与耗时。
- 新场景帧间隔及 P95。
- UI 主循环和 Display 线程耗时，保持并行线程口径独立。

只有实现完成、相关正确性检查通过、性能结果与证据记录完成后，才将本方案状态更新为“已完成”。如果主要瓶颈转移，应单独报告新的耗时分布。

## 7. 路径优化实施与验证记录（2026-09-27）

### 实际实现

- `ExternalVisionBindingDevice` 保留原始 `source_path`，新增运行时 `source_base_dir` 和 `source_path_key`。项目保存逻辑未改变，派生键不写入项目文件。
- `include/corona/utils/scene_path_key.h` 统一绑定和场景资源的规范化规则：UTF-8、`weakly_canonical`、失败时对已确定的绝对路径作词法规范化、Windows ASCII 大小写折叠。相对绑定来源必须提供绝对的场景/项目基目录；缺失或模糊的盘符相对路径抛出 `invalid_argument`，不会发布半成品绑定。
- `SharedDataHub::set_external_vision_binding()` 只信任私有表内已生成的键。来源和基目录未变时复用；首次绑定、来源或基目录变更时重建。调用方携带的过期键不会被信任，文件系统操作在元数据锁外完成，随后一次性发布完整绑定。
- Actor C++/Python API 增加可选的 `source_base_dir` 参数。现有绝对路径调用保持兼容；相对路径调用需要显式补上基目录。编辑器传入项目根目录，重载仍走清除/重建绑定入口。
- 场景加载事件在接收时固定绝对路径和基目录。旧文件加载 API 的相对路径在接收时按当时工作目录解释，不再依赖稍后渲染线程的工作目录；嵌入场景的相对键按其资源基目录解释。
- 显式场景重载调用 `refresh_external_vision_binding_paths()`，也刷新保留的 Actor；可直接在 Hub setter 指定 `refresh_source_path=true`，或清除再绑定。刷新只发布派生键，保留期间发生的无关字段修改。运行中目录链接变化不做逐帧轮询。
- `sync_external_live_vision_transforms()` 和 `has_external_live_bindings_for_scene()` 的逐绑定来源比较直接读取派生键；移除了同步函数中临时补算场景键的分支。

### 正确性与构建验证

现有 `corona_network_protocol_tests` 新增路径身份回归，覆盖首次绑定、等价绝对/相对路径、Windows 分隔符和大小写、`..`、UTF-8、不同场景隔离、工作目录变化、来源修改、基目录迁移、清除重建、显式刷新、无关字段保留、空来源和缺失基目录拒绝。开发顺序先加入测试，确认新工具缺失导致构建失败，再实现并通过测试。

额外临时计数和 Windows junction 测试已通过：目录联接从 A 改向 B 后，仅修改可见性/形状索引仍保持 A 的键且解析计数不变；显式重载刷新后取得 B 的键；强制刷新单个绑定准确增加一次解析。临时测试补丁保存在 `path-count-tests.patch`，固定本机夹具路径，不能作为跨平台通用测试直接使用。

运行回归也检查了 kitchen 的实际状态快照：隐藏/恢复、物体移动/还原期间 86 帧，绑定累计解析计数全程 598；相机移动/还原另测 29 帧，累计计数仍全程 598。物体变更时同步日志出现 `changed=true`，相机位置快照确认移动生效并已还原。598 为加载期 299 次绑定初始化加 299 次显式加载刷新，不是逐帧工作。

构建使用项目规定的 `.agents/skills/clion-build-corona-engine/scripts/build.ps1`，无 CMake 配置或依赖改动。独立代码审查未发现需修复的正确性问题。采样后恢复正式源码、永久回归测试和原始 `scene.ini` 字节；最终构建及 `corona_network_protocol_tests` 均退出 0，预期 `corona_engine.exe` 存在，源码无临时计数器，采样进程已退出。

### 性能结果

RTX 3070 Ti、CLion RelWithDebInfo，kitchen 299 个物体，1 spp、最大深度 16、PT 实际启用 SVGF。预热 20 秒，采样 25 秒，共 **163** 个新场景帧；全部稳态同步 `changed=false`。实际 framebuffer **1536×825**；相机快照与基线除运行时句柄外完全一致。未改 AABB、PT、SVGF 或渲染参数。

| 指标 | 优化前均值 | 本轮均值 | 本轮 P95 |
|---|---:|---:|---:|
| 每帧绑定来源规范化次数 | 299 | **0** | **0** |
| 每帧绑定来源规范化耗时 | 31.581 ms | **0 ms** | **0 ms** |
| CPU 同步总耗时 | 164.937 ms | **133.543 ms** | 136.671 ms |
| AABB 重算次数 | 299 | **299** | 299 |
| AABB 重算耗时 | 131.152 ms | **131.394 ms** | 134.359 ms |
| 新场景帧间隔 | 187.514 ms | **153.737 ms** | 157.821 ms |
| UI 主循环间隔 | 18.611 ms | 17.551 ms | 18.522 ms |
| Display 单次更新耗时 | 0.528 ms | 0.552 ms | 0.830 ms |

零耗时表示没有执行绑定路径规范化，不表示字符串比较无成本。计数器覆盖所有线程的绑定初始化/刷新入口；163 帧的累计值最小和最大都为 598，既验证同步内零调用，也排除了帧间或其他线程偷偷补算。AABB 仍遍历 1,443,303 个三角形/帧，占本轮同步耗时约 98.4%。

新场景产生速度约 **6.50 FPS**。旧整帧基线 133 帧、旧细分基线 136 帧和本轮来自不同采样轮次，表格用于观察变化，不应混合不同轮次计算精确阶段加速比。UI 和 Display 是并行线程，不能与 Optics 时间相加。原先“同步降至数毫秒”的目标依赖尚未实施的 AABB 优化，本轮没有达到、也没有声称达到该目标。
