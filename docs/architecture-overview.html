03七种通信语义

模块之间没有"统一消息总线"。实际存在七种语义明确、彼此不可替代的通道。 理解它们是理解整个引擎的前提。

C1 · 共享槽位 SLOT

SharedDataHub 持有 13 个 Kernel::Utils::Storage<T,128,2>。 每个槽位一把 std::shared_timed_mutex，读写通过 RAII 句柄 ReadHandle/WriteHandle 自动加解锁。 容量硬上限 128×2 = 256 个对象，满了会新开一个 StaticBuffer 分段。

  • 语义：最新状态，就地覆盖，无队列、无历史。
  • 谁在用：DAG 内部（系统之间直接读写对方拥有的字段，例如 Optics 读 GeometryDevice）。
  • 风险：try_acquire_write() 在默认编译配置下不是非阻塞——CFW_ENABLE_LOCK_TIMEOUT 默认 0， 实际走的是 lock()（storage.h:29-30）。外部线程直接写槽位会阻塞在 DAG 的临界区上。

C2 · 命令队列 CMD

Kernel::CommandBuffer<Command, KeyOf, Policy>：有界、线程安全、单消费者。 生产者任意线程，消费者只有拥有者系统。

两种合并策略

  • LatestWins — 同 key 只保留最新一条。用于连续量：相机位姿、滑条、材质标量。
    入队即合并，队列满时挤掉最旧的 key（计入 Stats::dropped）。
  • Fifo — 按序全量投递，队列满时拒绝新命令（返回 false）。用于离散量：创建/销毁/注册回调。

两个额外能力

  • peek(key) — 读取"尚未被消费的最新命令"，这是"读己之写"的唯一干净实现。
  • merge() — 若 KeyOf 提供 merge(pending, next)，同 key 合并时只覆盖命令声明要改的字段， 保留其余字段。这是"两个滑条同时拖同一个物体"不丢更新的原因。

C3 · 只读快照 SNAP

Kernel::SnapshotChannel<Snapshot>：单发布者（拥有者系统，每 tick 一次）， 多读者（任意线程，任意时刻）。读者拿到的是 shared_ptr<const Snapshot>， 生命周期与 DAG 解耦——DAG 继续发布不会让手上的旧快照失效。

  • 为什么不是事件：面板一次刷新要读上百个 actor，订阅事件会变成"发 100 条并保证都被消费"。
  • 为什么不是命令：命令是写方向；拿它做读会让 get_* 退化成轮询 + 往返。
  • 临界区：只做一次 shared_ptr 拷贝，不持任何存储锁。

C4 · 同步事件总线 EV·SYNC

Kernel::IEventBus：publish() 会在发布线程上立即同步调用所有订阅者。 这是最容易被误用的一条通道。

它在跨线程时的真实行为

PlayAudioEvent 由 CEF / 脚本线程发布，AcousticsSystem（DAG 线程）订阅—— 于是 AcousticsSystem 的处理函数跑在调用者的线程上，只能先把事件塞进 pending_plays_ 再等自己 tick 消费（acoustics_system.h:79）。 同理 DisplaySurfaceRemovedEvent 由主线程发布，处理器必须只入队 + 带 promise 返回， 真正的拆除发生在 Display 的 update()。这就是"同步事件逼出异步队列"的实证。

C5 · 异步事件流 EV·ASYNC

Kernel::EventStream<T>：每个订阅者一条独立 deque + condition_variable + 背压策略（Block/DropOldest/DropNewest）。

但全仓库只有一个真实用户：EngineShutdownEvent（src/engine.cpp:197-199）， 且用 max_queue_size = 1, DropOldest 只做"有没有人要求关机"的一次性查询。 其余三条 get_stream<EngineShutdownEvent>() 都是同一个用途， 其余 EventStream 都是注释里的示例。它存在但基本闲置。

C6 · GPU 回执 GPU

不是线程原语，而是 GPU 异步导致的跨帧握手。生产者把图像写进 ImageDevice 时， 同时写入 submit_receipt；Display 合成完把消费回执写进 consumed_receipt； 生产者下次覆盖前必须等这个回执。配合 PublishedImage（绑定一次分配的生命周期令牌） 与 SurfaceFrameCoordinator（帧级读写仲裁）防止"重写到正在被读的图"。

05共享槽位与句柄模型

Storage 的内部形状

Storage<T, 128, 2>                      // 128 个/段，初始 2 段 = 256 槽
├── StaticBuffer[]  (segments)
│    ├── std::array<T, 128> buffer       // 值直接内联，句柄 = &buffer[i]
│    ├── std::array<std::atomic<bool>,128> occupied
│    ├── std::array<std::shared_timed_mutex,128> mutexes   // 每槽一把，读写锁
│    ├── std::vector<size_t> free_indices
│    └── std::mutex alloc_mutex          // 只在分配/回收时持
└── get_parent_buffer(addr)              // 按地址范围反查所属段
句柄性质当前实现后果
身份表示uintptr_t = 槽位元素的内存地址跨进程无意义（网络层必须另用 actor_guid 映射）
失效检测槽位 occupied=false 后地址可被复用（ABA）长生命周期任务必须带 epoch（例：GeometryDevice::import_epoch）
容量256 槽/类型（128×2）快照必须按有界数组设计；超出即分配失败而非无限增长
并发每槽 shared_timed_mutex（读写锁）"try_" 前缀不等于非阻塞（见 C1）
单写者纪律ThreadAffinity::assert_owner_thread() 运行期断言 + 头文件边界（编译期）越界写会记 ERROR 日志并累加 violations()
容量 128 是硬上限，而快照是"整份重发"

publish_camera_snapshot_from_storage() 每 tick 遍历整个 storage 重建 vector<Row>。 在 256 个对象、每行约 40 字节的规模下这是廉价拷贝；但一旦有人把蒙皮顶点或网格塞进快照， 每 tick 的拷贝成本就会变成新的事故源。快照只投影标量和小结构。

06启动与关闭时序

启动的关键决策点是顺序：DAG 不能在 initialize_all() 内部装配 （那时 SystemManager 持着非递归锁，get_system() 会重入死锁）， 所以装配被放在 initialize_all() 之后、run() 之前。

初始化阶段的六步

  1. KernelContext::initialize() — 建立 IEventBus、IEventBusStream（流注册表）、ISystemManager。
  2. register_systems() — 注册 8 个系统。此时只创建对象，不初始化。
  3. 注册 5 个资源解析器：Text / Image / Scene / Video / Audio。Scene 解析器显式打开 网格简化与自适应 LOD（engine.cpp:145-150）。
  4. sys_mgr->initialize_all() — 按 priority 降序调用 initialize()，任一失败即中止。
  5. configure_systems_dag() — 建图、编译、装 tick 边界钩子。 CORONA_SYSTEMS_DAG=0 可整体退回旧模式。
  6. run() — 先订阅关机事件流（必须在 worker 启动前，否则首个 update 失败会丢）， 再 start_all()，进入 60 FPS 主循环。
关闭顺序里有一条专门为 GPU 回执让路的设计

Engine::shutdown() 先调 UiSystem::teardown_main_surface_before_stop()， 再 stop_all()。原因：主 surface 拆除需要 Display（DAG 线程）兑现回执； 如果先停 DAG，拆除请求没人处理，会等满 10 s 超时 + SDL 关闭再等 5 s， 退出多耗约 15 秒且 swapchain 不释放（ui_system.h:48-58）。

07单 tick 执行流程

DAG 线程是 FrameGraph::run_tick() 的唯一调用者，全部节点内联在该线程上执行。 不把节点甩到 worker 线程是刻意选择：引擎的系统数据依赖通过 SharedDataHub 的槽锁暴露， 跨线程执行会让"谁在持锁"重新变得不可预测。先要确定的执行序，不是吞吐。

为什么四个重链路都是 phase = 0

它们同相位意味着"要么一起跑、要么一起不跑"，这样 60 Hz 的那一 tick 里 Mechanics → Geometry → Optics 是同一帧的因果链；错相位会让 Optics 读到上一 tick 的几何， 正是文档里记录过的"同一帧里 Geometry 读到 Mechanics 上一帧刚体"那类不可复现时序问题。

08渲染帧与呈现链路

为什么要三层回执

回执写入者等待者解决什么问题
SubmitReceipt生产者（渲染提交队列）消费者查询完成GPU 命令是否执行完
consumed_receiptDisplay（合成完）生产者（下次覆盖前）"这张图还在被读，别重写"
PublishedImage 令牌生产者（发布时拷贝）Display（取图像时）句柄数值被复用后，旧帧不能误取新槽位

PublishedImage 的注释把问题说得很清楚：Display 的快照可能比生产者的退休（retirement）活得更久， 即使数值句柄已经被另一个生产者复用，也不能拿到旧槽位。这与 surface 退休是两件事—— 空闲的 optics 层可以消失，而 surface 和 UI 继续呈现。

18已知裂缝与风险

以下每一条都能在源码里定位，不是推测。

#裂缝级别证据与影响
1try_acquire_write 实际是阻塞的高CFW_ENABLE_LOCK_TIMEOUT 默认 0，因此 try_acquire_write() 走 lock()（storage.h:29-30, 707）。CEF 快路径的 14 处写会阻塞在 DAG 的槽锁上。要么改成真正的 try_lock，要么全部走命令。
2网络线程直写槽位高SyncEngine 在 Network 线程里 try_acquire_write 写 ModelTransform / Optics / 其他 Storage（sync_engine.cpp:494-526），绕过了命令通道。远程写与本地 CEF 写之间没有仲裁，与第 5 节"槽位对外部线程不可见"的约束冲突。
3同步事件总线的跨线程调用中PlayAudioEvent（CEF/脚本线程 → Acoustics）、ScriptFinishStartEvent（Python 线程 → UI）都会在发布者线程执行订阅者代码。目前靠 pending_plays_ 缓冲兜住，但这是一种"必须记得加队列"的隐性约定。
4位掩码位号曾经撞车中CameraStateUpdateField::ViewSettings 原本占用 1u<<17，与 FollowsDefaultSurface 冲突后改到 1u<<18（源码有注释）。位 6、7 仍空洞。新增字段必须查空位。
5默认值不一致低CameraMoveCommand::fov 默认 45，CameraDevice::fov 默认 60。若某条路径只构造命令不填 fov，相机会被悄悄改成 45°。
6命名漂移低EnvironmentDevice::sun_position 存的是方向；EnvironmentUpdateCommand::sun_direction 写入 sun_position；OpticsDevice::bEnableLighting 仍是匈牙利前缀。读代码时容易误解语义。
7句柄 = 地址的三个后果中① 跨进程无意义（网络层必须另设 guid→seq 映射）② 槽位复用有 ABA 风险（已有 import_epoch 这类补丁）③ 长期方案是 index + generation。CommandBuffer 的 key 也是 uintptr_t。
8快照整份重建中每 tick 遍历整个 storage 重建 vector<Row>。当前廉价，但一旦有人把重载荷（蒙皮/网格）投影进快照，成本会随实体数×载荷线性上升。约定：快照只放标量。
9Actor→组件解析要拿 5–6 把锁中resolve_actor_geometry_handles() 是 actor → profile → {mechanics,optics,acoustics} → geometry 的链式锁。CEF 每个 actor 每次刷新都调一次。这不是并发效率问题，是读路径形状错了——应该是一次快照读。
10EventStream 基本闲置低9 个事件头、47 个结构体里，只有 EngineShutdownEvent 真正走 EventStream；其中 19 个 *DemoEvent 无发布者无订阅者。要么删，要么在注释里标清"示例"。
11命令入口不统一低13 条命令队列分散在 shared_data_hub.h 与 6 个领域头里。git grep enqueue_ 仍有多个入口。P5 的目标是"只剩统一入口"，尚未达成。
12两种线程模型并存低CORONA_SYSTEMS_DAG=0 会退回"一系统一线程"。两条路径的时序保证不同（DAG 模式下 dt 由调度器注入，传统模式下系统自测），降级路径的行为需要单独验证。
13120 Hz / 60 Hz 双层节拍低四个重链路 period_ticks=2，Display 每 tick 都跑。奇数 tick 上 Display 拿到的仍是上一帧的 optics 内容，需要靠 ScenePresentCadence 判断"重复呈现旧帧"并跳过 present。这条逻辑一旦漏判就会白烧 GPU。
最该先修的一条

第 1 条（try_acquire_write 阻塞）与第 2 条（网络线程直写槽位）是同一类问题的两面： 外部线程仍在直接碰槽位。命令化的收益（可合并、可排序、可回执、单一仲裁点）只有在 "所有外部写都走命令"时才成立；留下几个直写口子，仲裁就重新变成不可推理的。

一句话总览

CoronaEngine 的架构可以压成一句话：一条线程按 DAG 顺序跑五个系统， 所有跨线程交互都收敛成"写走命令、读走快照、通知走事件"三条语义明确的路径， 共享状态放在带句柄的槽位池里，外部只能通过命令和快照间接接触它。 这个模型已经落地了大部分（13 条命令队列、6 条快照通道）， 剩下的主要工作是把仍在直写槽位的少数外部路径（网络、部分 CEF 快路径）也收进命令通道。
