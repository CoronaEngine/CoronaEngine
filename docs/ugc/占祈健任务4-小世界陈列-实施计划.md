## 1. 对「美术直接摆放在小世界内」的理解

参考 [HUD 计划](占祈健任务2-小世界UI变化-实施计划.md) 的取舍，本项实现为：

> **主世界产出的物质，在小世界里以真实场景物件陈列出来，并逐世界持久化。**

理由：主世界目前唯一能产出的物质是**世界碎片**（击败巨龙后掉落 → 拾取计数 `inventory.worldFragment`）。
"直接摆放"的字面含义是"不需要布景编辑器就能把它放进小世界"，因此设计为
**按固定陈列点顺序布置**，而不是做一套自由拖拽的编辑器（那属于马鹏程的栏位系统）。

---

## 2. 数据模型

### 2.1 陈列物注册表（`storyProps.mjs`）

```js
STORY_PROPS = [{ id: 'world-fragment', name: '世界碎片', itemKey: 'worldFragment',
                 asset: 'fragment/Ball.obj', height: 0.5, description: ... }]
```

数据驱动，新增物质只需加一条。`itemKey` 对应背包里那个计数器。

### 2.2 陈列点（`PLACEMENT_SITES`）

四个固定点位（西/东/北/南），**不依赖场景编辑器**：第 N 件陈列物用第 `N % 4` 个点位。

### 2.3 身份规则

| 项 | 规则 |
| --- | --- |
| 物件 GUID | `story.placement.<4位序号>`，由序号**确定性生成** |
| 序号分配 | 取**最小空位**，删除一件不会让其它件重编号 |
| 归属判定 | 只有 `story.placement.` 前缀的 actor 会被本功能管理，**绝不碰用户美术** |

> 归属判定这条是硬约束，抄自 [storyActors.mjs:63-69](CoronaEngine/game/frontend/storyActors.mjs#L63-L69) 的既有铁律。

## 3. 存储位置：一个必须讲清楚的契约

陈列存档 **`<小世界所属的 link owner>/.game/story-placements.json`**，**不是**小世界目录自己的 `.game/`。

原因（这是实施中实测确认的）：
- 主子世界共用**同一份** `.game` 元数据，`story-link.json` 就存在 link owner 那边
- 导航锁 `story-navigation.lock` 也只在 link owner 的 `.game` 下
- 写在那里，读写才能与「复制/恢复世界」事务**互斥**

实测验证：

```
主世界/.game/story-link.json                  ← 关联
主世界/.game/story-placements.json            ← 陈列（在这里）
主世界/.game/subworld/.game/story-link.json   ← 子世界只有关联
```

**主世界读到的永远是空布局**——所以主世界不显示陈列栏，也不允许写入（后端直接拒绝并返回「只有小世界可以陈列主世界取得的物质」）。

## 4. 持久化实现（`placements.py`）

沿用 `story_gameplay.py` 既有范式：

- **原子写**：临时文件 → `fsync` → `os.replace`
- **失败即拒绝**：存档损坏/超限时**抛错且不覆盖原文件**
- 上限：64 件、64 KB

校验规则（`validate_state` / `validate_placement`）：
`version==1`、`index` 为非负整数且唯一、`position`/`rotation` 为三元有限数、`scale` 为正有限数。
**注意 `bool` 是 `int` 子类**，所以用 `type(v) in (int, float)` 而非 `isinstance`。

---

## 5. 场景同步（`syncPlacementActors`）

**布局是权威来源**，每次同步：

1. 删除布局里已不存在的 `story.placement.*` actor（撤回立即生效）
2. 按序号顺序创建/复用/移位剩余陈列物
3. 等待真实 AABB 后再决定落地高度

关键实现点：

- **落地高度**：存储的 `y` 是**地面线**，物件要站在上面，所以 `y - bounds[1] * scale`。
  AABB 未就绪时不能猜，否则物件会沉进地面 → 复用 `ensureStoryCharacters` 的轮询写法。
- **复用而非重建**：已是目标缩放的实例直接沿用其现有 scale，避免每次同步都重设缩放。
- 关闭物理、纠正 `visible`/`follow_camera`，与角色流程一致。

## 7. 实施中发现并修复的 3 个真实缺陷

### 7.1 `unwrapGameplay` 不认识 CEF 桥的真实返回形状 ⚠️ 最重要

CEF scratch 桥对按键事件的返回是 **`{ response: '<JSON 字符串>' }`**，
而 `unwrapGameplay` 原来只处理 `.data` 包装、且从不解析字符串。

后果：**任何经此桥的响应校验实际都可能失效**。这是既有代码的隐患，本轮因为陈列请求才暴露出来。

修复：解开 `response` 并在解析失败时原样返回（不抛错），同时把 `{errors:[...]}` 形状转成异常。
修复后 `load`/`save` 与战斗操作共用同一套解析。

### 7.2 `flush()` 只在 `visualDirty` 时才重绘

`savePlacements` 起初没有标记 `visualDirty`，导致布局存盘成功、面板数字正确，**但场景里没有物件**。
这是"测试逼出来的"——面板断言全过，只有"actor 是否真的存在"这条挂了。

### 7.3 撤回不生效（测试脚手架自身的 bug）

mock 里 `removeActor` 对 `const` 数组做了重新赋值，静默失败。改为原地 `splice`。

> 7.3 是测试代码的问题，但它教会一件事：**只断言"面板数字"是不够的，必须断言"场景里真的有/真的没了"**——这正是最终测试的写法。
